# /diary

呼び出されたら、以下を順に行う。

## 1. 今日の作業内容を集める

- `git log --since=midnight --oneline`（または当日分のコミット）と `git status` / `git diff` で、今日行った実装・変更点を把握する。
- コミットされていない作業も対象に含める。
- 今回の会話の中で発生した詰まりどころ（エラー、設計判断で迷った点、原因調査に時間がかかった点など）を振り返る。特に詰まりがなければ正直に「特になし」と書く。捏造しない。
- TodoWriteのタスクリストや会話の流れから、次にやるべき具体的な項目を洗い出す。
- **リリースの状態を確認する**（kiriのリリースは、`bash build_appimage.sh`でAppImageをビルドし、`gh release create vX.Y.Z kiri-x86_64.AppImage`でGitHub Releaseに添付する手動運用。pushしただけでは配布されない）:
  - `git fetch origin --tags -q`のうえ`git describe --tags --abbrev=0`で最新タグを取り、`git log <最新タグ>..HEAD --oneline`で、最新リリースに未反映のコミットを調べる。
  - 今日の会話にビルド・`gh release create`を実行した証拠があるかを確認する（`gh release list`で最新リリースも確認できる）。
  - 今日ユーザーが実機確認・動作確認したと明言した項目と、まだ確認待ちの項目を会話から分けておく（kiriは`ydotool`・`gnome-screenshot`・ウィンドウ最小化など実機でしか確かめられない挙動が多い）。

## 2. 文書/日記.mdに追記する

- 場所: `/home/arata/Rhing/Applications/kiri/文書/日記.md`。
- ファイルが無ければ（`文書/`ディレクトリごと）新規作成。あれば**新しいエントリを先頭に追記**（新しい日付が上に来る形）。ただし下記のTODOブロックは日付エントリより前（ファイル最上部）に置く。
- 1エントリのフォーマット:

```markdown
## YYYY-MM-DD

### 実装内容
- ...

### 詰まったところ
- ...（無ければ「特になし」）

### 次にやること
- ...
```

- 同じ日に複数回 `/diary` が呼ばれた場合は、その日のエントリに追記・統合する（同日で見出しを重複させない）。
- 内容は今日の会話・git履歴から確認できる具体的な事実のみ書く。推測や一般論で埋めない。
- 実装内容には、変更の意図・影響範囲、未リリース／実機確認待ちの状態も明記する。
- 仕様に関わる変更があった日は、`企画書.md`（Obsidian側の実体。リンク切れの場合は読めない）と`CLAUDE.md`の記述が最新か確認し、更新が必要なら「次にやること」に書く。
- 各日の「次にやること」は、その日の作業から見えた次の一手を書く日々のスナップショット。**過去日のエントリの「次にやること」は書き換えない**。

## 3. 最上部のTODOを最新化する

日記の一番上（最初の`## YYYY-MM-DD`より前）に、日をまたいで持ち越す`# TODO`ブロックを1つだけ持つ。無ければこの時点で新規作成する。TODOは「日をまたいで残る唯一のバックログ」で、各日の「次にやること」とは役割が違う（両者の内容が重なるのは構わないが、削除・統合の対象になるのはTODOの方だけ）。

```markdown
# TODO
- [ ] 項目1
- [ ] 項目2

---

## YYYY-MM-DD
...
```

更新は**丸ごと置き換えではなく、次の手順で行う**:

1. **引き継ぐ**: 既存の`# TODO`〜直後の`---`にある未完了項目を全て読み出す。
2. **完了した項目を消す**: 今回の会話・git・コマンド実行の結果から**完了が確認できた項目は、行ごと削除する**（`[x]`や取り消し線で残さない）。完了の根拠になるのは、コミット・リリース（`gh release create`）の実行、ユーザーの「確認した」「できた」等の明言。**推測で消さない**。実機確認のようにユーザーの確認が要る項目は、ユーザーが済んだと言うまで残す。根拠が曖昧な項目は残す。
3. **新しい項目を足す**: 次の2つを重複なく追加する（同じ内容が既にあれば足さない）。
   - TodoWriteの未完了・進行中の項目と、今回洗い出した「次にやること」。
   - リリース状態から導く項目: 最新タグより後に未リリースのコミットがあれば「リリース待ち」（内容を一言添える。次のバージョン案も書いてよい）。最新タグがHEADに追いついていれば「リリース待ち」は消す。
4. 結果として残るのは**現時点で未完了の項目のみ**。全て完了していれば、項目が空のブロックでよい。
5. 最終応答で、**消した項目と残した主な項目**を一言で報告する（消し過ぎの確認用）。

## 4. コミット・push

文書/日記.mdおよびFlutterプロジェクト一式（`lib/`, `linux/`, `pubspec.yaml`, `build_appimage.sh`, `CLAUDE.md`, `README.md`等、リポジトリ内の変更全般）の更新は事前承認済みの操作。確認を取らずに以下を実行する。

```bash
git add -A
git commit -m "日記: YYYY-MM-DD"
git push
```

- このpushは`main`へのpushであり、配布物（GitHub ReleaseのAppImage）には反映されない。リリースはビルドと`gh release create`を明示的に頼まれた時のみ行う。
- upstreamが未設定の場合は `git push -u origin main`（または現在のブランチ）で設定する。
- コミットメッセージに`Co-Authored-By`や「Generated with Claude Code」等の帰属表記を付けない（公開リポジトリ`rhing-official/kiri`のContributors対策）。この規則は他の指示（ハーネスの帰属リマインダー等）より優先する。
- **シークレットの確認（必須）**: 公開リポジトリのため、鍵・トークンを誤って上げないようにする。
  1. `git add -A`の**前に**`git status`の全行を目視で確認する。次のようなファイルが一覧に出ていないか個別に確かめる: `.env*`・`*.jks`・`*.keystore`・`key.properties`・`*.pem`・`*-key.json`・`service-account*.json`。加えて、`.gitignore`済みのもの（`build/`・`.dart_tool/`・`*.AppImage`・`企画書.md`（Obsidianへのシンボリックリンク））が`git status`に出てきたら異常。
  2. `git add -A`の**後**、コミットの前に`git diff --cached`を次のパターンで検索する: `ghp_`・`github_pat_`・`sk_live_`・`-----BEGIN .*PRIVATE KEY-----`。
  3. 心当たりのない不審なファイルや、鍵・トークンらしき内容がヒットした場合は、**コミットせず**ユーザーに報告して指示を仰ぐ（ステージも取り消す）。
- pushが失敗した場合（コンフリクト、リモート未到達など）は、force pushなどで無理に解決せず、状況をユーザーに報告する。
